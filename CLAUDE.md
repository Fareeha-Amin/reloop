# ReLoop

Circular donation & redistribution platform. Donors with reusable household goods
(clothes, toys, books) are matched to verified recipient organisations. The point of the
project is what happens **after a rejection**: re-rank, escalate to the donor, and fall
back to paid recycling — so every donation ends in reuse or material recovery.

Full background: `docs/ReLoop_Project_Context.pdf`
Build brief and phase plan: `PROMPT.md`

**Stack:** FastAPI · PostgreSQL · SQLAlchemy 2.x + Alembic · Pydantic v2 · pytest ·
React 19 + Vite + Tailwind + React Router + TanStack Query + Leaflet/OSM · in-process sweeper (no Celery/Redis; see Decisions) · Scikit-learn / TensorFlow
behind interfaces.

## How we work

Build **one phase at a time**. For each phase:

1. Short plan first — the files you'll create or change. Then build.
2. Unit tests for anything deterministic.
3. End with: what you built, exact commands to run it, and an acceptance test I can do
   by hand.
4. **STOP** and wait for "next phase".
5. Update this file with any new decision, command or env var.

Push back when a requirement is confused, over-engineered, or would paint us into a
corner. Say so before building it.

## Non-negotiables

1. **Every donation reaches a defined end state.** Terminal states have no outgoing
   transitions. Outcome states are `COMPLETED` (reuse) and `RECYCLED` (recovery).
   `CANCELLED` is terminal but is a donor withdrawal, not an outcome. Every donation the
   donor does not withdraw ends in reuse or recovery. No state can be entered but not left.
2. **The lifecycle is an explicit transition table**, not conditionals scattered across
   route handlers. Tests assert that terminal states have no outgoing edges and that
   every non-terminal state can reach an outcome state.
3. **Rejections are data.** Never delete or overwrite a `Match` row.
4. **One source of truth for every constant.** Category weights, carbon factor, fee
   percentages, thresholds — defined once, imported everywhere. A test pins this.
5. **The score explains itself.** Ranking is decomposable into its factors and surfaced
   as reasons, never a bare number.
6. **A stub says it is a stub** — in the code, in the comments and in the README. No
   `TODO` presented as a shipped feature.
7. **Nothing fails silently.** An unroutable donation surfaces to an admin queue.
8. **Estimates are labelled as estimates.** Mass and carbon figures are modelled, not
   measured.
9. **Config over hardcoding.** Weights, caps, thresholds and fees live in configuration
   so they can be tuned and measured.
10. **Donor addresses are sensitive.** Approximate location during matching; precise
    address released only after acceptance, and logged when released.
11. **Scoring and lifecycle logic are pure functions**, decoupled from the database, so
    they are unit-testable and reusable in a simulation.
12. **The API is the only source of truth.** No business logic in the React layer.

## Environment

`.env.example` gains a variable **the moment code reads it, never before.** A speculative
env file goes stale within a week and then lies about what the project needs.

| Variable            | Added in | Purpose                                                                                                                                                                                              |
| ------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`      | Phase 0  | Postgres connection string                                                                                                                                                                           |
| `SECRET_KEY`        | Phase 0  | JWT signing                                                                                                                                                                                          |
| `TEST_DATABASE_URL` | Phase 1  | Separate pytest database. **Every table in it is dropped** at the start of a run; the tests refuse to start if it names the `DATABASE_URL` database. Unset → DB tests skipped (shown in the summary) |
| `SWEEPER_ENABLED`   | Phase 2  | Run the deadline sweeper inside the API process every `SWEEP_INTERVAL` (default `true`). `tests/conftest.py` forces it `false`                                                                       |

Every other Phase 2 tunable (weights, boosts, TTLs, `LISTED_STALL`, `SWEEP_INTERVAL`, timeouts, fee, category weights) is in `app/constants.py`.

Phase 3 adds no environment variables. The frontend reads none: its API base (`/api`), polling intervals and map defaults are in `frontend/src/config.ts`, and the dev proxy target (`http://127.0.0.1:8000`) is in `frontend/vite.config.ts`.

Phase 3 part 3 adds no environment variables either. New tunables: `CHAT_MESSAGE_MAX_LENGTH` in `app/constants.py`; `POLL_MS.chat` and `READ_KEYS_MAX` in `frontend/src/config.ts`.

Phase 4 adds no environment variables either. New tunables, both in `app/constants.py`: `LOGISTICS_PLATFORM_FEE_PCT` (independent of `RECYCLING_PLATFORM_FEE_PCT`, even though both start at 10%). Pricing for a `LogisticsProvider` (base fee, per-km rate) lives on its row, not in config, same as a `WasteCollector`'s rate.

Impact metrics, the handover-path fix and the recycling-choice entry point add no environment variables. New tunable: `CARBON_FACTOR_KG_PER_ITEM` in `app/constants.py`, a per-category placeholder beside `CATEGORY_WEIGHT_KG`, under the same `CATEGORY_WEIGHTS_ARE_PLACEHOLDERS` flag.

# all commands run from backend/ with the venv active (.venv\Scripts\Activate.ps1)

# install dependencies

# create a migration (review it: StrEnumType renders as sa.String(length=32))
alembic revision --autogenerate -m "describe the change"

# apply migrations
alembic upgrade head

# create an admin (password is prompted; admins cannot self-register)
python -m app.cli create-admin --email admin@example.org --name "Platform Admin"

# create the test database (once, as a Postgres superuser; the reloop role lacks CREATEDB)
psql -U postgres -c "CREATE DATABASE reloop_test OWNER reloop;"

# seed Bengaluru organisations, recyclers and a demo donor (idempotent; one shared password, prompted)
python -m app.cli seed

# apply every due deadline now (the API also sweeps in-process every 15 min; safe to repeat; real clock only)
python -m app.cli sweep

# write the OpenAPI schema the frontend's types are generated from (a test fails if it is stale)
python -m app.cli export-openapi
```

```
# frontend commands run from frontend/ (Node 24 LTS)

npm run check:api

npm test

Every other `HELD_STATES` reader — address release (`matching.holder`), capacity (`matching.held_quantities`), chat (`chat.OPEN_STATES`), and the acceptor branch of the notification feed — stays on `HELD_STATES` alone | Recycling never holds an organisation's slot or address: adding `WASTE_REDIRECTED`/`RECYCLING_IN_TRANSIT` to `HELD_STATES` would have leaked an old acceptance's address, capacity count, chat access and notifications to an organisation that no longer has the donation. Checked by `test_only_stall_leaves_booked_states_without_completing` (over `BOOKED_STATES`, not `HELD_STATES`) |
| `Handover.match_id` becomes **nullable**; `Handover` gains a nullable `recycling_id` (unique, FK to `recyclings.id`). **Exactly one of the two is enforced by a database CHECK constraint** (migration `0007`), not only in application code | The one deliberate exception to "no CHECK constraints repeating vocabulary values" (see the row below on that): this CHECK protects a structural invariant across two nullable foreign keys, not a vocabulary value, so it belongs in the database. `Booking.handover_id` needed no change: a `Booking` already only cares which `Handover` it points to, not whether that handover belongs to a match or a recycling |
| **Booking a recycler pickup schedules it; a separate donor action records the hand-over** (the donation-pickup split, mirrored). `BOOK_RECYCLER_PICKUP` now lands in a new state, `RECYCLING_SCHEDULED`, not `RECYCLING_IN_TRANSIT`. The donor then sends `MARK_RECYCLER_HANDED_OVER` (new action, new donor edge `RECYCLING_SCHEDULED → RECYCLING_IN_TRANSIT`), which also sets the booking's `picked_up_at`. A new action rather than reusing `MARK_HANDED_OVER`, because that action's copy and its acceptor-side meaning are donation-specific. `RECYCLING_SCHEDULED` stalls after 72h (`STALL`, like `ACCEPTED`) and is in `BOOKED_STATES`, so the refund hook covers it | Before this, booking jumped straight to `RECYCLING_IN_TRANSIT`: the donor had no way to record the hand-over, and admin `CONFIRM_RECYCLED` was open the moment a courier was booked, before the goods had left the donor. Admin confirmation now needs the hand-over step, as it does for `WASTE_REDIRECTED` drop-offs |
| `logistics.book_recycler_pickup` reuses the same `Booking`/`Payment`/wallet/commission machinery as an organisation's platform pickup, to the assigned `WasteCollector`'s address instead of an accepting organisation's. The sweeper's refund hook (`cancel_and_refund`) now checks both an organisation booking and a recycler booking (`_open_booking`); at most one is ever open, since whichever leg preceded the current one was already closed by its own `STALL` | No new booking machinery: a platform pickup is a platform pickup regardless of its destination. The refund test (`test_only_stall_leaves_booked_states_without_completing`) now runs over `BOOKED_STATES`, so it still catches a future edge that bypasses `STALL` out of either an organisation's hold or a recycler handover |
| The donor pays a recycler pickup exactly as a donation pickup: the wallet is optional (clamped, never raises on a zero balance), the rest by simulated checkout | Consistent with the existing donation-pickup decision; no new payment rule to reason about |
| `STALL_TIMEOUTS[RECYCLING_IN_TRANSIT] = 48h`, same as `IN_TRANSIT` | Both are "a booked/self-reported handover in progress, no further news expected soon" |
| **Admin `CONFIRM_RECYCLED` no longer has an edge directly from `WASTE_REDIRECTED`** — a deliberate behaviour change, not an oversight. Four existing tests were updated to add the donor's handover step before confirming: `test_acceptance_script.py`, `test_impact_and_recycle.py`, `test_logistics_and_wallet.py` (via its shared `_credit_wallet` helper), `test_recycling_and_admin.py` | Before this change an admin could confirm recycled the moment a donation was redirected, with no record that the goods ever left the donor. `lifecycle.states_awaiting(Actor.ADMIN)` now reads `{NEEDS_ADMIN, RECYCLING_IN_TRANSIT}`, so `WASTE_REDIRECTED` also drops out of the admin notification feed and `GET /admin/awaiting` until the handover is recorded |
| `RecyclingOut` (the donor's and admin's view of a recycling assignment) gains the collector's `address_text`/`latitude`/`longitude` and the donor's own `handover` record (null until recorded) | The collector's address is a business address, not donor-sensitive, so it is shown plainly (unlike an organisation's, released only on acceptance) — the donor needs it to know where to take the goods, or to confirm where a booked courier is headed |
